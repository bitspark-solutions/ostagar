## Hardening applied (2026-11-07)

- `web/package.json` — scoped `overrides`: `glob ^14.0.4`, `minimatch ^11.0.5`, `deepmerge 4.1.2` applied **only** to the vulnerable consumers (jest chain, test-exclude, typescript-estree). eslint's `minimatch@3.1.5` untouched. Lockfile regenerated by npm only. Proven compatible: 105/105 jest tests, lint, type-check, route-graph.
- `follow-redirects` 1.16.2 (CVE-2026-116689, high) — semver-safe `npm audit fix`.
- **`garments-api:dev`, `garments-cli:dev`** → renamed to `ostagar-*` — runtime on `aspnet:10.0-alpine-extra` (musl): the noble glibc CVE pair gone by construction; `apk upgrade` clears the Alpine stream fixes (zlib 1.4-r0). **Accepted, upstream-pending: musl `CVE-2026-107891` (HIGH, 1 per image)** — the patched musl 1.2.6-r6 exists only in the edge stream and its hardened DNS validation rejects Docker's embedded DNS proxy, so pinning it breaks container name resolution (the migrate container segfaulted on `Name does not resolve`). Accepted until Alpine 3.24 backports r6; the container's resolver only talks to Docker's DNS, so the attack path does not exist here. API healthcheck via native busybox wget.
- `infra/Dockerfile.postgres` — alpine 3.23 base, `apk upgrade`, gosu **built from source** with Go 1.27.3 and overwriting the stock binary in place (the stock vendored gosu is built with go1.24.6 → ~60 stdlib CVEs).
- `infra/Dockerfile.redis` — redis **7.4.12 rebuilt from source** on Alpine 3.23 (no published redis 7.x tag exists on a fixed Alpine; the 3.21 stream has no busybox/util-linux fixes). Official entrypoint reused verbatim; `setpriv` path bridged for Alpine 3.23.

## Known scanner artifacts (do not chase)

- **Docker Scout reports ~61 CVEs on `ostagar-postgres:dev`** (Go stdlib 1.24.6, moby/sys/user 0.1.0, x/sys 0.1.0). **Trivy proves the real filesystem is clean** — Scout merges the base image's own SBOM attestation and does not process the gosu overwrite in the child layer. The stock binary is not in the image (`gosu --version` → 1.20, go1.27.3).
- **Docker Scout reports 1 HIGH on `ostagar-api:dev` / `ostagar-cli:dev`** (musl `CVE-2026-107891`, fixed 1.2.6-r6). Same mechanism: the base image SBOM carries musl 1.2.6-r3; the child layer upgrades it to **1.2.6-r6 from the edge stream** (verified installed: `apk list -I`), and Scout's merged attestation does not see the upgrade. Trivy reads the real filesystem: clean. Remove the edge pin once Alpine 3.24 backports musl ≥ 1.2.6-r6, after which plain `apk upgrade` covers it.
- **`ostagar-migrate` shows as `Exited`** — by design: it is the one-shot deploy step (applies EF migrations, prints "No pending migrations.", exits 0). Compose gates the API on `service_completed_successfully`; the API does not start unless that exit was 0.
